## S1 — A crashed huddle member deadlocks the whole run, permanently and silently

**New finding.** Nothing bounds or supervises a sub-team huddle turn.

- `src/team.ts:186` and `src/team.ts:204` — `await io.ask(...)` with no timeout.
- `src/orchestrator.ts:1614-1622` — `askMember` registers a one-shot resolver in
  `pendingTeamReply` and returns a promise that is *only* settled by the member's outbox
  watcher. It never sets `pendingSince`.
- `src/orchestrator.ts:2438` — the role-liveness watchdog iterates `pendingSince`, so a
  huddle member is never in its scope; `src/orchestrator.ts:2439` skips `teamOwner` members a
  second time.
- `src/orchestrator.ts:2310` — `recoverRole` returns immediately for any role in `teamOwner`,
  so even the child-exit path (`armChildExit`, `src/orchestrator.ts:2282`) cannot recover it.
- `src/orchestrator.ts:2476` — the orchestrator-progress watchdog returns without nudging or
  halting whenever `teamOwner.size > 0`.

**Failure scenario.** `teams: true`, autoComplete run. The orchestrator emits
`TEAM: pair members=alpha,beta`. `alpha`'s child process is OOM-killed mid-turn. Its outbox is
never written, so `pendingTeamReply.get("alpha")` is never fired; `runHuddle` awaits forever;
`teamOwner` never empties; every watchdog branch that could halt the run is gated off by
`teamOwner`. The run hangs with no HALT, no transcript entry, no `endedAt` stamp, and the
journey driver blocks behind it indefinitely. Only `--stop` / SIGTERM ends it.

**Smallest fix.** Give `askMember` a deadline and a liveness check. In
`src/orchestrator.ts:1614`, wrap the returned promise in `Promise.race` against a timer of
`(role.turnTimeoutSec ?? 600) * 2` seconds; on expiry, delete the resolver and resolve with
`"[HUDDLE TIMEOUT] <role> did not reply"` so `runHuddle` proceeds (it will hit its own
`maxRounds` cap and return `capped`). Additionally, in `armChildExit`
(`src/orchestrator.ts:2283`), before the `recoverRole` call, fire any pending
`pendingTeamReply` resolver for that role with a `[MEMBER DIED]` string so the huddle unblocks
on the same tick the process dies.

## S2 — A slow verify-on-reply can HALT a perfectly healthy run

**New finding.** The per-reply verify introduced in 1.7.0 does not set the `verifying` flag the
progress watchdog checks.

- `src/orchestrator.ts:1220` — `let verifying = false`.
- `src/orchestrator.ts:1533` / `1540` — only `handleGatedCompletion` sets and clears it.
- `src/orchestrator.ts:1834` — verify-on-reply calls `runVerify` (default timeout 600s,
  `src/persist.ts:228`) inside the outbox watcher, with `verifying` left `false`.
- `src/orchestrator.ts:1816` — the replying seat's `pendingSince` entry was already deleted.
- `src/orchestrator.ts:2460` / `2476-2488` — with `verifying === false`, `orchBusy === false`,
  `pendingSince.size === 0` and `teamOwner.size === 0`, the watchdog counts the wait as an idle
  deadlock: two nudges at `ORCH_STALL_MS` (10 min default) apart, then `haltRun`.

**Failure scenario.** A single-seat autoComplete run with `verify.cmd = "npm test"` taking
~9 minutes. The seat replies; verify-on-reply starts. At +10 min the watchdog sees no in-flight
turn and no pending role, and posts a nudge; `nudgeOrch` calls `postEvent`, which spends a real
orchestrator turn on a run that is not stuck. With `MD_AGENT_ORCH_MAX_NUDGES=0` (or two slow
verifies in a row) it calls `haltRun` and tears the run down mid-verify — writing `HALT.txt`
and, in a journey, stopping the phase.

**Smallest fix.** Set the flag around the per-reply verify exactly as the gate does. At
`src/orchestrator.ts:1833`, `verifying = true;` before the `runVerify` call and
`verifying = false;` in a `finally` around it.

## S3 — A seat kills itself for good because its *own report text* mentions quota

**New finding.** The exhaustion detector is run over the model's response, not just over
provider-level error channels.

- `src/claude.ts:59-61` — `looksExhausted` matches, among others, `/rate limit(ed| exceeded)/i`,
  `/quota (reached|exceeded|exhausted)/i` and `/resets in \d/i`.
- `src/agy.ts:227` — `const everything = \`${String(obj?.response ?? "")}\n${err}\n${out.slice(-2000)}\`` —
  `obj.response` is the assistant's own text.
- `src/agy.ts:228-231` — a match rejects with `ProviderExhaustedError`.
- `src/role.ts:360-362` → `stopSelf` (`src/role.ts:313`) writes `stopped` into `state.json`
  and `process.exit(0)`s the seat.

**Failure scenario.** An agy seat is asked to summarize a rate-limiting incident, review this
repository's own budget code, or draft release notes mentioning "quota exceeded". Its correct,
successful reply contains the phrase. md-agent discards the reply, marks the seat permanently
stopped in `state.json`, tells the orchestrator to never dispatch to it again, and exits the
process — on a turn where the provider returned `status: SUCCESS`. Nothing in the transcript
says the seat was healthy. Note the `/resets in \d/i` alternative fires on ordinary prose such
as "the window resets in 3 hours".

**Smallest fix.** Exclude the assistant's own text from the probe. At `src/agy.ts:227`, drop
`String(obj?.response ?? "")` from `everything`, leaving `${err}\n${out.slice(-2000)}` — the
stderr and raw-stream channels where agy actually reports quota. If a response-text signal is
still wanted, gate it on `status !== "SUCCESS"`.

## S4 — A quota-stopped seat is never revived, even after the window it recorded resets

**New finding.** `stopped.resetsAt` is written but never read.

- `src/role.ts:322` — `mine.stopped = { …, resetsAt: err.resetsAt }` persisted to `state.json`.
- `src/persist.ts:148` — `RoleSpec.stopped?: { at; handoffTo?; reason?; resetsAt? }`.
- `src/orchestrator.ts:1082` — on resume, `roles.map((r) => (r.stopped ? null : spawnRole(…)))`.
  There is no comparison of `resetsAt` against `Date.now()` anywhere in `src/` (the only other
  `resetsAt` reads are `WindowSnapshot`'s unrelated field at `src/orchestrator.ts:1268`).
- `src/orchestrator.ts:2316-2323` — the live watchdog likewise refuses to respawn.

**Failure scenario.** An agy seat exhausts its weekly Antigravity quota on Monday and records
`resetsAt` = next Monday. The user resumes the run the following Tuesday. The seat is still
dead: not respawned, printed as "stopped (abandoned)", and the orchestrator's system prompt
(`src/orchestrator.ts:293`) tells it to never dispatch there — with the misleading text
"STOPPED by the user". Recovering it requires hand-editing `state.json`.

**Smallest fix.** In `resumeOrchestrator`, before `src/orchestrator.ts:1082`, clear expired
self-stops:

```ts
for (const r of roles) {
  if (r.stopped?.resetsAt && r.stopped.resetsAt * 1000 <= Date.now()) {
    console.log(`[orchestrator] seat "${r.name}" quota window has reset — reviving`);
    delete r.stopped;
  }
}
await updateState(runDir, { roles });
```

(Leave user stops, which have no `resetsAt`, untouched — that is what distinguishes the two.)

## S5 — `budget.usd` cannot bind an agy seat: agy spend is always recorded as $0

**New finding.** A hard USD ceiling is silently unenforceable on the provider whose quota the
baseline report says was actually burned.

- `src/agy.ts:321-330` — `extractUsage` returns `costUsd: 0` unconditionally ("cost is not
  computed here (no price table)").
- `src/persist.ts:493` — `recordUsage` sums that zero into the seat's cost file.
- `src/orchestrator.ts:1271` — the `usd` axis reads `total.costUsd`.
- `src/orchestrator.ts:1273-1274` — `fiveHourPct` / `sevenDayPct` come from
  `WindowSnapshot`, which `AgySession.lastWindows` (`src/agy.ts:82-84`) always returns `null`
  for. Only the `tokens` axis (`src/persist.ts:412`) counts agy at all.

**Failure scenario.** A team of three agy seats is launched with
`budget: { usd: { soft: 20, hard: 40 } }` and no `tokens` limit — the shape the wizard and
`src/init.ts:33` most naturally suggest. Three axes out of four are structurally blind to every
agy seat, and the fourth is unset. `checkBudget` (`src/orchestrator.ts:1265`) iterates, finds
`a.value == null` or `0` on every axis, and never halts. The run spends the entire weekly
Antigravity cap with a budget configured and apparently active in the dashboard.

**Smallest fix.** Make the blindness loud rather than silent. At run start (next to
`preflightAgents`, `src/orchestrator.ts:1078` / the launch path), when any role has
`provider === "agy"` and `budget.usd`/`fiveHourPct`/`sevenDayPct` is set but `budget.tokens`
is not, print and transcript a warning: `agy seats report no cost and no plan windows — only
budget.tokens can bind them; set one or these ceilings will not fire.` A follow-on (larger)
change is a per-provider quota-unit table so agy spend has a number at all.

## F5 — One agy turn is still unbounded in steps and tokens; the escalation path still re-runs the whole task

**Baseline finding 5: partly fixed.** Real progress landed; the specific mechanism named in the
baseline is still uncapped.

What is fixed:

- A per-turn **wall-clock** cap now exists — `src/persist.ts:155` (`turnTimeoutSec`),
  `src/role.ts:103` (default 300s agy / 600s claude), enforced at `src/agy.ts:172-180` and
  `src/claude.ts:250-260`, and stated to the seat in its mandate at `src/role.ts:120`.
- Session recycling by turn count *and* by size — `src/role.ts:49` (`DEFAULT_RECYCLE_TURNS = 8`)
  and `src/role.ts:64-69` (`RECYCLE_TOKENS = 200_000`), applied at `src/role.ts:276-279`.
- The **earlier verify point** the baseline asked for exists: `src/orchestrator.ts:1830-1863`
  verifies every seat reply in that seat's own workspace, and a seat that claims done while the
  check fails gets the output straight back without an orchestrator turn
  (`src/orchestrator.ts:1849-1858`).
- A deterministic loop guard — `src/orchestrator.ts:2660-2679`.

What still holds:

1. **No per-turn step or token cap.** `src/agy.ts:139-150` builds the argv: `-p`,
   `--output-format`, `--conversation`, `--model`, `--add-dir`, permission args,
   `--print-timeout`. There is no step or token limit passed, and no accumulator in the
   stdout handler (`src/agy.ts:181-192`) that counts `step_update` events or `usage` and kills
   the child. A 100-step, 6M-token turn runs to completion as long as it finishes inside 300s
   — and an agentic loop re-sending a large context is exactly the shape that stays under a
   time cap while blowing a token cap.
2. **Recycle-by-tokens is retrospective.** `src/role.ts:275-279` reads
   `session.lastUsage` — i.e. it recycles *after* the 6M-token turn has already been paid for,
   before the next one. It bounds the second occurrence, not the first. The comment at
   `src/role.ts:46-48` acknowledges this ("This bounds growth, not baseline").
3. **A verify bounce still re-runs the whole task once the ladder engages.**
   `src/orchestrator.ts:1553-1567` → `escalateRolesTo` (`src/orchestrator.ts:1488-1523`) kills
   and respawns **every** non-pinned seat and clears their inboxes and outboxes
   (`src/orchestrator.ts:1515-1516`), then posts a re-attempt event. That is a whole-team
   restart triggered by one failing check.

**Smallest fix (per-turn token cap).** In `src/agy.ts`, parse the `usage` field off each
`step_update` line already being split at `src/agy.ts:187-191`, accumulate `total_tokens`, and
when it exceeds a cap (`opts.turnTokenCapSec`-style option, default ~1_500_000, env
`MD_AGENT_AGY_TURN_TOKENS`), `child.kill()` and reject with the same "re-scope it smaller"
message the timeout path uses at `src/agy.ts:179`. This reuses the existing kill/reject shape
and needs no new supervision loop. A step cap is the same edit against a counter of
`event === "step_update"` lines.

**Smallest fix (scoped retry).** In `src/orchestrator.ts:1556`, restrict escalation to the
seats that actually failed: change `escalateRolesTo(tier)` to take the set of role names with a
non-zero entry in `seatVerifyFails` (`src/orchestrator.ts:1868`) and intersect it with
`climbing` at `src/orchestrator.ts:1493`.

## F1 — agy seats are now bound to their worktree, but nothing proves the isolation held

**Baseline finding 1: partly fixed.** The spawn no longer omits the directory.

- `src/agy.ts:146` — `args.push("--add-dir", this.cwd ?? process.cwd())`, on **every** turn.
- `src/agy.ts:164` — the child's process `cwd` is also set to the seat's directory.
- `src/role.ts:166-175` / `src/role.ts:186` — `workspaceDir` comes from `provisionWorkspace`
  and is passed through `makeSession`'s `common.cwd`.
- Fixed in `94b28b9` ("agy seats bind to their directory").

Residual gap: `--add-dir` *grants* a directory; it does not *replace* agy's default project.
Neither `--new-project` nor `--project` is passed anywhere in `src/` (verified by grep across
`src/`, `skills/`, `README.md`, `smoke-agy.ts`), and the code comment at `src/agy.ts:142-145`
states the concern in its own words: "a worktree seat would write into whatever project it last
knew". More importantly, **nothing checks afterwards whether isolation actually held**:
`reportWorkspaces` (`src/workspace.ts:113-164`) inspects only `<runDir>/workspaces/<role>`. If
an agy seat wrote into the repo root, the end-of-run audit reports every workspace as clean and
says "safe to merge" while the user's tree has been edited underneath them.

**Smallest fix.** Turn the assumption into a check. In `stopAll`'s worktree branch
(`src/orchestrator.ts:1713`), before printing the per-seat reports, snapshot the repo root:
capture `git -C process.cwd() status --porcelain` at run start (next to the
`provisionWorkspace` calls) and again here, and if the two differ under `isolation:
"worktree"`, print a loud `ISOLATION BREACH — the repo root changed during an isolated run:
<diff>` line above the merge advice. `workspace.ts` already has the `git()` helper
(`src/workspace.ts:11`) and `workspaceHasChanges` (`src/workspace.ts:79`) to build on.
Separately, if `agy --new-project <dir>` exists, add it at `src/agy.ts:146` on the first turn
of a seat (guarded by `!this.conversationId`) so the worktree is the project, not an addendum.

## F3 — The reviewer seat is still never routed to; the loop is only capped, not redirected

**Baseline finding 3: partly fixed.** The idle-reviewer shape is now discouraged and bounded,
but no code path dispatches to a reviewer.

Mitigations that landed:

- `src/orchestrator.ts:324` — the system prompt tells the orchestrator that "an idle reviewer
  while a worker loops on verify is the wrong shape". This is advice to a model, not a rule.
- `src/orchestrator.ts:1849` — the direct bounce is capped at `verify.maxFailures` (default 2,
  `src/persist.ts:226`); past that the failure is attached to an event the orchestrator sees
  (`src/orchestrator.ts:1860-1861`), so it can re-route.
- `src/orchestrator.ts:2660-2679` — the ping-pong guard warns at 4 and halts at 6 consecutive
  dispatches to the same seat.

Still present:

1. Nothing in `src/` selects a reviewer. There is no notion of a reviewer role, and no branch
   that, on repeated failure, dispatches the failing output anywhere other than back to the
   failing seat or to the orchestrator's discretion.
2. The ping-pong guard is defeated by alternation. `src/orchestrator.ts:2665-2669` resets
   `pingPongCount` to 1 whenever the dispatch target differs from the last one, and
   `resetPingPong()` (`src/orchestrator.ts:1838`, `2680`) fires only on a verify PASS. An
   orchestrator that alternates `worker` → `helper` → `worker` → `helper` never reaches
   `PINGPONG_WARN`, so the loop that "burns a week of quota on cache reads" — the exact case
   the guard's comment cites — runs unbounded as long as two seats are involved.

**Failure scenario for (2).** `worker` fails verify. The orchestrator asks `helper` to look at
the failure, then re-dispatches `worker`, then `helper` again. `pingPongCount` never exceeds 1.
Fifty round trips later there has been no verify PASS, no HALT, and no warning.

**Smallest fix.** Make the guard count *dispatches since the last verify PASS*, not consecutive
dispatches to one seat. At `src/orchestrator.ts:2664`, keep the per-seat counter for the
message text but add `dispatchesSinceVerifyPass++` on every `notePingPong` call, reset it only
in `resetPingPong()` (which already runs solely on PASS, `src/orchestrator.ts:1838`), and trip
the same warn/halt thresholds at, say, 8 and 12 against that counter. Two lines of state and
one extra condition; it closes the alternation hole without changing the existing behaviour for
the single-seat case.

## S6 — The completion gate verifies each workspace alone; the merge is never verified

**New finding.**

- `src/orchestrator.ts:1893-1910` — `runGate` collects every dirty workspace and runs verify in
  each one separately, ANDing the results.
- `src/orchestrator.ts:1744-1754` — the end-of-run audit reports per-branch PASS and prints
  "safe to merge: <branches>".

**Failure scenario.** `seat-a` renames `parseConfig` in its worktree; `seat-b` adds a new caller
of `parseConfig` in its worktree. Both branches pass `npm test` in isolation, so `runGate`
returns `ok: true`, the run completes as "phase complete (verified)", and the audit prints
"every seat passed verification / safe to merge: a, b". Merging both produces a tree that does
not compile. The run's central promise — "here is which branch is safe to merge" per
`src/workspace.ts:100-105` — is not what was checked.

**Smallest fix.** Add one integration check to `runGate` when `dirty.length > 1`: create a
scratch worktree at `<runDir>/workspaces/.merged` from the base HEAD, `git merge --no-commit`
each dirty seat's branch into it, run verify once there, and fold the result into `ok`. Report a
merge conflict itself as a FAIL with the conflicting paths as the tail. Reuse
`workspaceBranch` (`src/workspace.ts:25`) and the existing `runVerify`.

## S7 — Verify runs on every seat reply, including replies that changed nothing

**New finding.**

- `src/orchestrator.ts:1830` — the condition is `if (verify && !wasStopped && !stopping)`. There
  is no check that the seat's workspace changed since the last verify, even though
  `workspaceHasChanges` (`src/workspace.ts:79`) exists and is used in `runGate` sixty-plus
  lines later (`src/orchestrator.ts:1899`).

**Failure scenario.** A three-seat run with `verify.cmd = "npm test"` (90s). Seats report status
frequently, as `src/role.ts:113-118` explicitly instructs them to ("do ONE slice of the ask per
turn… then REPORT"). Over 40 replies — many of them pure status, analysis, or "blocked on X"
with an untouched workspace — that is an hour of test runs. This compounds with S2: each one is
a window in which the progress watchdog can misfire.

**Smallest fix.** At `src/orchestrator.ts:1830`, add a guard: skip the verify when the seat has
a workspace and `!(await workspaceHasChanges(ws))`, unless `claimsDone(content)` (a completion
claim from a seat that changed nothing is itself worth checking). Two extra clauses; the import
is already present at `src/orchestrator.ts:9`.

## S8 — A completion requested during an in-flight verify is dropped without a word

**New finding.**

- `src/orchestrator.ts:1532` — `if (!verify || stopping || verifying) return;`

**Failure scenario.** A gated completion is running (`verifying === true`). A role reply lands,
the pump takes a turn, and the orchestrator emits `[[PHASE-COMPLETE]]` with no TO: blocks.
`orchTurn` calls `handleGatedCompletion` (`src/orchestrator.ts:1391`), which returns instantly
on the `verifying` guard. Nothing is logged, nothing is posted back, and `orchTurn` returns `""`
— so `handleReply` prints "no direct dispatch this turn" (`src/orchestrator.ts:2562`). The run
now has no pending role work and no in-flight turn; it sits until `ORCH_STALL_MS` elapses.

**Smallest fix.** At `src/orchestrator.ts:1532`, split the guard: when the early return is
caused by `verifying`, `await postEvent("[SYSTEM/verify] A verification is already running for a
previous completion request; wait for its result before emitting [[PHASE-COMPLETE]] again.")`
rather than returning silently.

## S10 — `runVerify`'s timeout kills the shell, not the test process

**New finding.**

- `src/orchestrator.ts:1457` — `spawn(spec.cmd, { shell: true, cwd })`.
- `src/orchestrator.ts:1460-1467` — on timeout, `child.kill()` (SIGTERM to the shell only).

**Failure scenario.** `verify.cmd = "npm test"` hangs. At `timeoutSec` md-agent kills
`/bin/sh`; the `npm` process and its jest/vitest workers are reparented to init and keep
running. Over a long run with several verify timeouts, orphaned test processes accumulate and
contend for CPU with the live seats, making later verifies slower and more likely to time out —
a self-reinforcing failure that looks like flaky tests.

**Smallest fix.** Spawn detached and kill the process group: add `detached: true` at
`src/orchestrator.ts:1457`, and at `src/orchestrator.ts:1462` use
`process.kill(-child.pid!, "SIGTERM")` inside the existing try/catch (fall back to
`child.kill()` on Windows, where `detached` has different semantics).

  explicitly and is passed through by `resolveModelFor` (`src/persist.ts:110-114`).
- Consistent in the planner's seat table (`src/plan.ts:77-79`) and the README

## Lower-severity notes (no separate fix recommended)

- **`claimsDone` is a keyword heuristic.** `src/orchestrator.ts:1872-1877`. "the type checks are
  complete failures" tests true (the negative lookaround at `src/orchestrator.ts:1875` does not
  cover it), so a seat honestly reporting failure is told "You reported done, but the check
  fails" (`src/orchestrator.ts:1855`). Confusing, not harmful — the seat gets the failing output
  either way (`src/orchestrator.ts:1861`).
- **Escalation overwrites a concrete model id with a tier name.**
  `src/orchestrator.ts:1504` — `r.model = tier` on a seat configured as
  `"model": "gpt-oss-120b-medium"` silently moves it onto the tier ladder. `escalate: false`
  (`src/persist.ts:164`) is the documented opt-out, but a seat that named a concrete id has
  arguably already opted out.
- **The preflight probe spends a real provider turn per run and per resume.**
  `src/orchestrator.ts:160-165`, called from `src/orchestrator.ts:1078`. Cheap (haiku/flash-low,
  "reply with: ok"), but on a weekly-capped plan it is not free, and `--resume` runs it every
  time. `MD_AGENT_SKIP_PREFLIGHT=1` exists.
- **`stopAll` exits 0 on HALT.** `src/orchestrator.ts:1778`. A `--launch` caller cannot
  distinguish a halted run from a completed one by exit code; only `HALT.txt` distinguishes
  them, which is why `src/journey.ts:245` reads the file. Fine for the journey driver, a trap
  for any other scripted caller.
